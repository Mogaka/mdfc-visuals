Component deployment summary

Use this table to map deployment choices to the underlying operational components.

Component Deployment pattern What it enables Notes
Registry Access Agentless / Hybrid Container Registry VA, runtime container VA (registry-based), gated deployment Needed whenever image content must be pulled directly from the registry.
K8S API Access Agentless Agentless discovery, attack path analysis, CIS benchmark, runtime VA inventory, XDR response actions Low-footprint path for runtime inventory and posture enrichment.
Agentless Scanning for Machines Agentless / Hybrid Runtime container VA (drift), runtime node VA, malware detection on nodes Snapshot-based assessment on underlying nodes or machines.
Defender Sensor (DaemonSet) Agent-based / Hybrid Runtime detections, drift detection, antimalware, DNS detection, gated deployment, hybrid runtime VA discovery Required for runtime telemetry-heavy scenarios and many XDR-aligned features.
Defender Sensor via Helm Agent-based Binary drift blocking, DNS detection, antimalware Explicit Helm-based path called out for select runtime protection features.
Azure Policy for K8s Agent-based Workload hardening (data plane) Delivered through AKS add-on or Arc extension depending on cluster model.

Plan comparison

Licensing path summary for common architecture questions.

Plan Primary coverage in this diagram Typical use in architecture decisions
Defender for Containers Most runtime, discovery, vulnerability, and control plane features across all lanes Choose when you need broad container security coverage, especially runtime detection and sensor-backed capabilities.
Defender CSPM Agentless discovery, attack path analysis, CIS benchmark, registry VA, selected runtime VA paths Choose when posture management and agentless security insights are the primary requirement.
Defender for Servers P2 Runtime node VA and malware detection on nodes Choose when node- or machine-centric protection is the requirement, especially outside pure container-runtime needs.
Free Control plane hardening and workload hardening (data plane) Use as a baseline security posture layer even when premium runtime capabilities are not yet deployed.

Deployment Decision Tree

Fast path guidance for technical teams: if you need a specific outcome, deploy the minimum viable mechanism below.

If you need broad vulnerability coverage without cluster agentsDeploy Registry Access and, if node/container runtime context is needed, add K8S API Access or Agentless Scanning for Machines.
If you need runtime detections and Linux workload alertsDeploy Defender Sensor. This is the core path for runtime alerting, drift detection, DNS detection, and XDR-linked features.
If you need drift blocking, DNS detection, or antimalwareDeploy Defender Sensor via Helm because the feature set explicitly calls for the Helm-based sensor path.
If you need posture and attack path visibility with minimal footprintDeploy K8S API Access and use the agentless lane for discovery, CIS benchmark, and attack path analysis.
If you need runtime container VA but prefer sensor-driven inventoryChoose the hybrid model: Defender Sensor for discovery plus registry pull or disk snapshot for scanning.
If you need node VA or malware analysis on worker nodesDeploy Agentless Scanning for Machines; add the applicable plan path (Containers, Servers P2, or CSPM depending on the feature).
If you need admission/policy hardening rather than runtime telemetryDeploy Azure Policy for K8s for workload hardening. This is separate from Defender Sensor-based runtime capabilities.
If you need XDR hunting or response workflowsDeploy Defender Sensor; for response actions, also provide K8S API Access.

Architecture shorthand: agentless minimizes cluster footprint, agent-based unlocks deeper runtime telemetry and enforcement, and hybrid is the bridge when discovery should be in-cluster but scanning should remain off-cluster.
